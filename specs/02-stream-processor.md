# Spec 02 — Stream processor Lambda

## Goal

A Lambda attached directly to the `Transactions` table's DynamoDB Stream
(native event source mapping). For each new transaction, compare `amount`
to a configurable threshold; if notable, publish an enriched JSON message
to the `transaction-alerts` SNS topic.

## Decisions needing sign-off before implementation

1. **Project-wide Java version is now 21, not 25.** AWS Lambda's managed
   Java runtimes top out at `java21` — there's no managed `java25` runtime
   to deploy to, and keeping local/CI on 25 while Lambda ran 21 would be a
   persistent split with no upside (nothing in this project needs
   Java-25-only features). `README.md`, `CLAUDE.md`, and `ci.yml` are
   updated to Java 21 as part of this phase; `services/stream-processor`
   targets `java21` throughout (Maven compiler release, Terraform
   `aws_lambda_function.runtime`).

2. **`transaction-alerts` SNS topic is created in this phase, not Phase 3.**
   `ACTION_PLAN.md` lists the topic under Phase 3, but Phase 2's own
   definition of done requires validating on LocalStack that this Lambda
   actually publishes to it — which needs the topic to exist. Resolution:
   `terraform/modules/sns-sqs-fanout` (currently an empty placeholder) gets
   *only* the `aws_sns_topic` resource in this phase. Phase 3 extends the
   same module with the `fraud-review-queue`/`customer-notification-queue`
   SQS queues and subscriptions — the module is built incrementally, not
   recreated.

## Interface / contract

### Transaction item shape (first phase to actually write items)

Phase 1 only fixed the key schema. This phase fixes the item shape the
stream processor reads:

| Attribute | Type | Required | Notes |
|---|---|---|---|
| `accountId` | S | yes (PK) | |
| `transactionId` | S | yes (SK) | |
| `amount` | N | yes | compared to threshold; missing/non-numeric → record is skipped and logged, not thrown (avoids poisoning the shard on a single bad item) |
| `type` | S | no | passed through to the alert if present (e.g. `DEPOSIT`/`WITHDRAWAL`/`TRANSFER`) |
| `createdAt` | S | no | passed through if present (ISO-8601) |

### `services/stream-processor` (new Maven module, Java 21)

- Handler: `RequestHandler<DynamodbEvent, Void>`, one handler class.
- Only `INSERT` stream records are processed (new transactions); `MODIFY`/
  `REMOVE` are ignored — matches "for each new transaction" in
  `ACTION_PLAN.md`.
- Threshold: env var `THRESHOLD`, default `10000`. Notable = `amount >
  threshold` (strictly greater than, matching README's "over a threshold"
  wording — exactly-at-threshold is **not** notable).
- On notable: publish to SNS topic ARN from env var `SNS_TOPIC_ARN`, JSON
  body:
  ```json
  {
    "transactionId": "...",
    "accountId": "...",
    "amount": 12345.67,
    "threshold": 10000,
    "type": "WITHDRAWAL",
    "reason": "amount 12345.67 exceeds threshold 10000",
    "alertedAt": "2026-07-24T21:00:00Z"
  }
  ```
  (`type` omitted if absent on the source item. `alertedAt` is generated by
  the Lambda at publish time, not read from the item.)
- Uses AWS SDK v2 (`software.amazon.awssdk:sns`) for the publish call.
- Packaged as a shaded/uber jar (`maven-shade-plugin`) for Lambda
  deployment.
- Unit tests (JUnit 5 + Mockito, no LocalStack needed):
  - Record parsing: well-formed record → correct fields extracted;
    missing/non-numeric `amount` → record skipped, no exception.
  - Threshold boundary: amount above / below / exactly-at threshold.
  - SNS publish only invoked for notable records; payload shape asserted
    via a mocked SNS client.

### `terraform/modules/sns-sqs-fanout` (topic only, this phase)

Variables: `topic_name`. Outputs: `topic_arn`. Just
`aws_sns_topic.this`, nothing else yet.

### `terraform/modules/stream-processor-lambda`

Variables: `function_name`, `stream_arn` (from the `dynamodb-table` module
output), `sns_topic_arn` (from the `sns-sqs-fanout` module output),
`jar_path`, `threshold` (default `10000`).

Resources:
- `aws_iam_role` (trust policy: `lambda.amazonaws.com`) +
  `aws_iam_role_policy` scoped to exactly: `dynamodb:DescribeStream`,
  `GetRecords`, `GetShardIterator`, `ListStreams` on `stream_arn`;
  `sns:Publish` on `sns_topic_arn`; CloudWatch Logs write access scoped to
  this function's log group.
- `aws_lambda_function`: `runtime = "java21"`, handler pointing at the
  shaded jar's handler class, env vars `SNS_TOPIC_ARN` and `THRESHOLD`.
- `aws_lambda_event_source_mapping`: `event_source_arn = stream_arn`,
  `starting_position = "LATEST"` (don't replay pre-existing stream
  history on first deploy), small `batch_size` (10).

Outputs: `function_name`, `function_arn`.

### Env wiring

Both `terraform/envs/localstack/main.tf` and `terraform/envs/aws/main.tf`
add:
```hcl
module "transaction_alerts_topic" {
  source     = "../../modules/sns-sqs-fanout"
  topic_name = "transaction-alerts"
}

module "stream_processor" {
  source        = "../../modules/stream-processor-lambda"
  function_name = "stream-processor"
  stream_arn    = module.transactions_table.stream_arn
  sns_topic_arn = module.transaction_alerts_topic.topic_arn
  jar_path      = "${path.module}/../../../services/stream-processor/target/stream-processor.jar"
}
```

### Verification on LocalStack

No SQS subscriber exists yet (Phase 3), so verification is via CloudWatch
Logs rather than reading a queue:

1. `mvn -f services/stream-processor/pom.xml package` to build the jar.
2. `terraform apply` in `envs/localstack`.
3. Insert a notable transaction (`amount` > 10000) via
   `aws --endpoint-url=http://localhost:4566 dynamodb put-item`.
4. Tail the Lambda's CloudWatch log group via
   `aws --endpoint-url=http://localhost:4566 logs tail
   /aws/lambda/stream-processor`; confirm a log line showing the SNS
   publish succeeded (message ID logged) for that `transactionId`.
5. Insert a non-notable transaction (`amount` ≤ 10000); confirm the logs
   show the record was evaluated but *not* published.

## Out of scope for this phase

- SQS queues/subscriptions on `transaction-alerts` — Phase 3.
- Fraud review consumer Lambda / `FraudReviewCases` table — Phase 4.
- CI/CD deploy workflows — Phase 5.
- Actual deployment to real AWS — Phase 6 (this phase only guarantees the
  Terraform/runtime choice is AWS-valid, not that it's been deployed there).
- DLQ, bisect-on-error, or other event-source-mapping failure tuning beyond
  DynamoDB Streams' default retry behavior.
